# AGENTS.md

Projeto de TCC (escola): aplicação web Spring Boot 4.1.0 / Java 26 / Thymeleaf MVC para acompanhar checklists de instalação de portas em obras. Textos da interface, nomes de views e mensagens de commit são em português brasileiro — mantenha assim.

## Como buildar e rodar
- Use o wrapper do Maven. No Windows: `.\mvnw.cmd` (comandos aqui assumem PowerShell). Maven 3.9.16 fixado via `wrapper/maven-wrapper.properties` (o Maven em si não é garantido no PATH).
- Banco local de dev: `docker compose up -d mysql` (MySQL 8.4, padrões `localhost:3306`, db/user/senha todos `obracontrol`, sobrescrevíveis via `.env`; `.env` é gitignored, `.env.example` lista as variáveis).
- Rodar a aplicação: `.\mvnw.cmd spring-boot:run` (porta 8080). `docker compose up` também builda e roda o container da app.
- Testes: `.\mvnw.cmd test`. Classes `@SpringBootTest` cobrem context-loads, operações dos repositórios JDBC e cadastro de obras/consultas auxiliares via MockMvc. O perfil de teste usa H2 em modo MySQL com Flyway **desativado** e aplica `schema.sql`/`data.sql` (réplica enxuta de `sql/`) via `spring.sql.init.mode=always`; nunca toca no MySQL. Testes que gravam dados usam `@Transactional` para isolamento. `FrontEndConventionsTests` não usa Spring: lê os `.js` de `static/` e falha se um arquivo misturar a grafia em português (`apartamentoId`) e em inglês (`apartmentId`) do mesmo campo, o que geraria `ReferenceError` em tempo de execução — `node --check` não pega isso, porque só valida sintaxe. Usar só uma das duas grafias no arquivo é aceito de propósito (o front-end tem variáveis locais em português, como `estadoId` e o parâmetro `obraId`); renomear todas seria refactor cosmético.

## Pegadinhas de arquitetura (verificadas — não "corrigir")
- Persistência é 100% JDBC: `ObraRepository`, `InstaladorRepository`, `ApartamentoRepository` e `PortaRepository` (com.cursojava.ObraControl.repository) gravam no **MySQL real via `JdbcTemplate`** (`spring-boot-starter-jdbc`) contra o schema canônico de `sql/` (JOIN construtora/cidade devolvem os nomes que a UI espera; POST de obra recebe `CadastroObra` com `cidadeId` e `construtoraId`, valida vínculos existentes e não cria cadastros auxiliares). `CadastroRestController` expõe `/api/estados`, `/api/estados/{estadoId}/cidades` e `/api/construtoras` para os seletores. Não existe camada JPA/Spring Data. As classes de modelo (`Porta`, `Obra`, `Instalador`, `Apartamento`) são POJOs simples.
- O JS do front-end (`static/obra.js`, `static/instalador.js`, `static/apartamento.js`, `static/checklist.js`) chama **endpoints REST do próprio backend Spring** via URL relativa: `/api/obras` (`ObraRestController`), `/api/instaladores` (`InstaladorRestController`), `/api/apartamentos` (`ApartamentoRestController`) e `/api/portas` (`PortaRestController`) — todas JDBC → MySQL.
- Edição: `PUT /api/obras/{id}` recebe `CadastroObra`; `PUT /api/obras/{id}/status` recebe `AtualizacaoStatusObra` (`aberta`/`finalizada`) e é o único caminho que altera o status; `PUT /api/instaladores/{id}` recebe `CadastroInstalador` (`nome`, `telefone`), também usado no POST. Os serviços validam criação/edição e retornam 404 na consulta/edição de registros inexistentes. Obras retornam nomes, status e `cidadeId`, `estadoId`, `construtoraId` para preencher a tabela e os seletores. A tela de obras permite finalizar/reabrir manualmente, sem exigir 100% do checklist; os modais continuam reutilizados para criar/editar os demais dados.
- Apartamentos: `ApartamentoRestController` (`/api/apartamentos`, JDBC → MySQL) com `ApartamentoRepository`/`ApartamentoService`. `GET` exige o parâmetro `obraId`; `CadastroApartamento` (`numero`, `obraId`) alimenta POST/PUT; número repetido na mesma obra retorna 409. `quantidade_portas` **não é informado no cadastro**: o repositório o recalcula a partir de `COUNT(porta)` em cada gravação (`atualizarQuantidadePortas`). A tela `/apartamento` usa `static/apartamento.js` e filtra a listagem por obra.
- Portas e checklist: `PortaRestController` (`/api/portas`, JDBC → MySQL) com `PortaRepository`/`PortaService`. `GET` exige o parâmetro `apartamentoId`; `CadastroPorta` (`local`, `apartamentoId`, `instaladorId`) alimenta POST/PUT. As 5 etapas são colunas booleanas e viram o mapa `etapas` na resposta, na ordem do enum `EtapaPorta` (`montagem`, `fixacao`, `fechadura`, `vistas`, `acabamento`); o toggle é `PUT /api/portas/{id}/etapas/{nomeEtapa}` com corpo booleano e etapa desconhecida retorna 400 — o repositório traduz a etapa para a coluna por `switch`, nunca concatenando o valor da URL. O `instalador_id` é opcional e vem no mesmo `CadastroPorta` (`local`, `apartamentoId`, `instaladorId`) do POST/PUT; o `PortaService` valida a existência via `InstaladorRepository.buscarPorId` (nulo é aceito) e a coluna fica `NULL` quando o instalador é excluído (`ON DELETE SET NULL`), sem afetar `quantidade_portas`. A tela escolhe o instalador por um `<select>` na própria linha da tabela, que grava pelo mesmo `PUT /api/portas/{id}` (caminho único de escrita para local, apartamento e instalador). Como o `PortaService` altera portas, ele também chama `atualizarQuantidadePortas` dos apartamentos afetados. A tela `/checklist-apartamento` usa `static/checklist.js` (obra → apartamento → tabela de portas com um checkbox por etapa, select de instalador, progresso e criar/editar/remover).
- Dashboard: `/home` é renderizado no servidor pelo `DashboardController`, seguindo `controller` → `DashboardService` → `DashboardRepository` → JDBC. `DashboardRepository` busca o resumo geral, o progresso por obra (incluindo obras sem apartamentos/portas via `LEFT JOIN`) e a quantidade de portas por instalador (incluindo zero). O progresso de cada obra é a soma das 5 etapas concluídas dividida por `quantidade de portas × 5`, com percentual calculado no DTO `ProgressoObra` para funcionar igual em MySQL e H2. O dashboard apenas exibe o status; a alteração acontece na tela de cadastro de obras.
- Schema é gerido por **Flyway ativo no boot** (`spring.flyway.enabled=true`): migrações canônicas em `src/main/resources/db/migration/` (`V001__create_tables.sql` cria as tabelas, `V002__seed_data.sql` insere o seed e `V003__padroniza_charset_collation.sql` fixa `utf8mb4_0900_ai_ci`). O Flyway só roda na config principal; o perfil de teste o desativa (H2) e replica as restrições funcionais em `schema.sql`. Migrações novas seguem `V00N__descricao.sql`; migrations aplicadas nunca são editadas. **Não** aplicar `sql/001`–`002` à mão: num banco que já tem o schema pré-existente (aplicado manualmente), o boot falha com `Validate failed` — para dev, resetar o banco (`docker compose down -v` apaga o volume do MySQL e o Flyway recria tudo do zero; ou DROP DATABASE + CREATE DATABASE e deixe o Flyway recriar).
- O nome do pacote é de caixa mista: `com.cursojava.ObraControl` (casando com a classe da aplicação e os testes). Renomear para `com.cursojava.obracontrol` quebra pacotes/testes até tudo ser reorganizado junto — trate qualquer "correção" de caixa como um refactor grande e deliberado.

## Padrões do projeto
- **Idiomas**: campos do banco e textos exibidos ao usuário em pt-BR; nomes de **funções/métodos em inglês**.
- **Banco de dados**: PKs sempre como `id`; FKs sempre como `entidade_id` (ex.: `obra_id`, `apartamento_id`, `instalador_id`). Tabelas associativas (junção) usam `_` no nome (ex.: `obra_instalador`).
- **Camadas**: `controller` -> `service` -> `repository` (injeção via construtor). Restes novos sigam `PortaRestController`.

## Convenções
- Controllers MVC mapeiam URLs para nomes de views Thymeleaf em `src/main/resources/templates`; as views estendem `layout/base.html` (thymeleaf-layout-dialect).
- Os scripts em `sql/` são a fonte canônica do schema; mantenha-os em sincronia ao mudar tabelas (o Flyway não pega drift). Note que `sql/001`–`002` foram convertidos nas migrações `db/migration`; `sql/003`–`008` são queries de consulta usadas como referência.
- `target/`, `.env` e `.vscode/` são gitignored. A UI usa Bootstrap 5.3 + bootstrap-icons via CDN.
